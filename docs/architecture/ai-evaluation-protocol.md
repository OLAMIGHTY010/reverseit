# SMARTREVERSAL — AI/ML Evaluation Protocol and Quality Assurance (A0)

## 1. Overview and Quality Philosophy
In financial operations, an undetected exception creates customer distress, while an incorrect automated reversal causes permanent double loss. Therefore, AI/ML features in SMARTREVERSAL are subject to continuous, metric-driven evaluation before deployment.

**The Golden Baseline Rule (Section 6.1 #S14)**:
> No AI model may be deployed to production unless it is calibrated, proven against a deterministic rule baseline, and verified in shadow mode.

## 3. Metrics per Capability & Comparative Baselines

| Capability | Model Type | Evaluation Metric | Comparative Baseline | Acceptance Target (To be agreed with Ops & Risk) |
| :--- | :--- | :--- | :--- | :--- |
| **Investigation Summaries (A2)** | LLM / Prompt Template | - **Faithfulness**: % of statements verified by evidence bundle<br>- **Citation Precision**: % of cited evidence IDs that exist and support claim<br>- **Hallucination Rate**: % of ungrounded statements | Deterministic rule-based template summary | - Faithfulness: 100%<br>- Citation Precision: 100%<br>- Hallucination Rate: **0.0%** (Zero tolerance) |
| **Root-Cause Hypotheses (A3)** | Hybrid: Signature + LLM | - **Top-1 / Top-3 Accuracy** vs confirmed closure causes<br>- **Abstention Quality**: abstains when evidence is missing | Known error signature table | - Top-3 Accuracy > 90%<br>- Abstention on missing evidence: 100% |
| **Anomaly & Spike Detection (A4)** | Rolling EWMA + Isolation Forest | - **Time-to-Detect (TTD)** on injected spikes<br>- **False Alarm Rate** per 1,000 transactions | Fixed threshold (e.g., >20 failures/min) | - TTD < 60s<br>- False alarm rate < 1.0% |
| **Duplicate Likelihood (A5)** | Gradient Boosted Decision Tree (GBDT) | - **Precision / Recall**<br>- **PR-AUC**<br>- **Cost-sensitive Loss** (False duplicate weighted 10x higher than false negative) | Deterministic 30s account + amount + beneficiary rule | - Must exceed rule PR-AUC on borderline cases<br>- Zero false positives on legitimate repeat payments |
| **Pending Resolution Hazard (A5)** | Survival Analysis / Logistic Regression | - **Brier Score (Calibration)**<br>- Calibration curve slope (target 1.0) | Historical mean duration per rail | - Brier Score < 0.10<br>- Calibrated within ±5% across deciles |
| **Alert Parsing & OCR (A9)** | Local Regex + Vision/LLM fallback | - **Field-level Extraction Accuracy** (amount, date, ref, account tail)<br>- **Confidence Calibration** | Fixed string splitters | - Field accuracy > 98%<br>- Under-confidence routing to manual form |

## 4. Shadow Mode and A/B Evaluation Protocols

### Phase 10 Stage 1: Shadow Protocol (PL-02)
1. **Parallel Execution**: AI/ML models receive inbound transaction events simultaneously with existing operations teams.
2. **Read-Only / Silent Operation**: The model logs its anomaly scores, case summaries, root-cause tags, and duplicate scores to `ai_evaluation_logs`.
3. **Daily Divergence Audit**:
   - Compare AI-recommended root cause vs actual resolution tag applied by human analyst.
   - Flag any false positives or false negatives for review.
4. **Duration**: Minimum 14 business days across at least 10,000 transactions.

### Phase 10 Stage 2: Supervised Mode (PL-03)
1. Operations analysts use the workbench with AI summaries and advisory scores visibly tagged:
   `"AI-assisted, not verified — Confidence: Medium"`.
2. Analysts must confirm or edit suggestions; every confirmation, edit, or rejection is logged with actor ID and timestamp.
3. Analyst agreement rate is tracked weekly:
   $$\text{Agreement Rate} = \frac{\text{Accepted Suggestions}}{\text{Total Suggestions Rendered}}$$

## 5. Model Cards, Drift Monitoring and Rollback Procedures

### Model Cards Specification
Every model deployed to the model registry must maintain a versioned Model Card containing:
- Model Name, Architecture, and Hyperparameters.
- Training Data Snapshot Hash (date range, sample size, synthetic vs real).
- Target Capability and Permitted Scopes (e.g., `NIP transfers only`).
- Baseline Comparison Results (proving it beats the deterministic baseline).
- Known Blind Spots & Edge-Case Failure Modes.
- Effective From Date and Approver Signatures (ML Lead, Head of Ops, Risk/Compliance).

### Continuous Drift Monitoring (OPS-03)
- **Input Feature Drift**: Population Stability Index (PSI) and Kolmogorov-Smirnov tests on transaction amounts, velocity, and error code distributions.
- **Output Distribution Drift**: Weekly monitoring of anomaly score percentiles (p50, p95) and duplicate score distributions. A shift of $>15\%$ triggers an automated ops review alert.

### Rollback Procedure
If a model displays degraded performance, hallucinated outputs, or schema failures in production:
1. Operator trips the feature kill switch (`POST /v1/killswitch/feature/{feature_name}`).
2. Traffic instantly falls back to the deterministic template or rule baseline.
3. The model registry marks the current model version as `INACTIVE_DEGRADED` and rolls back to the previous stable checkpoint.
